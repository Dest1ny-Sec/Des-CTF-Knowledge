# 知识库有效性验证报告

> 2026-11-02 · 用 2026 山东省赛总决赛的 5 道题（Pwn1/Pwn2/Pwn3/Re1/Re3）实测

## 实验设计

**问题**：接入本知识库后，agent 的推理质量是否真的提升？

**方法**：对照实验。同一批题，比较「无知识库时的基线思路」与「知识库给出的卡片+陷阱」。

**关键约束**：这批题是 Linux ELF / Windows PE，运行环境是 macOS，
**没有 Docker/qemu user-mode**，无法实跑。因此本实验测的是**推理方向**，不是完整利用链。

---

## 实验结果

### 1. 用「题目描述」检索 → 严重误判

| 题目 | 描述 | 知识库推荐 | 正确方向 | 判定 |
|---|---|---|---|---|
| Pwn3 imgz | "名字 imgz，与图片有关" | **LSB 图片隐写** | 堆题（malloc/free） | ❌ |
| Re1 legacy_gateway | "PE32 控制台程序" | **ret2libc** | 逆向业务逻辑 | ❌ |

**结论：仅凭题目名/描述查知识库会错。** 中文 2-gram 把 "imgz" 联想到了图片隐写。

### 2. 用「真实逆向证据」检索 → 全部正确

| 题目 | 真实证据 | 知识库推荐 | 判定 |
|---|---|---|---|
| Pwn1 blindfmt | `printf(buf)` 无格式化参数，PIE，6KB | 格式化字符串 | ✅ |
| Pwn2 vmforge | 10KB PIE，疑似 VM | 自定义虚拟机逆向 | ✅ |
| Pwn3 imgz | 导入 malloc/calloc/free/memcpy，.text 0x7272 | **tcache/fastbin 堆利用** | ✅ |
| Re1 legacy_gateway | PE32 + MFC | （未命中专用卡） | ⚠️ |
| Re3 chain_lock_vm | 700KB 静态链接 stripped | stripped 定位 + 自定义 VM | ✅ |

## 核心发现

### 发现 1：知识库的触发条件是「证据」，不是「描述」

这是本实验最重要的结论。

- 题目**描述**是出题人的语言（"imgz 与图片有关"）
- 题目**证据**是程序的客观属性（导入了什么函数、.text 多大、有没有 PIE）

知识库的 `signal` 字段是按证据写的（"用户输入被直接 printf(buf) 使用"），
所以**必须先逆向，再查库**，而不是先查库再逆向。

正确的工作流：

```
错误:  看题名 → 查库 → 按推荐做
正确:  拆二进制 → 拿到证据 → 查库 → 核对陷阱 → 做
```

### 发现 2：领域判别缺失会导致灾难性误导

修复前，Pwn3（堆题）Top-1 是 `ret2libc`，因为证据里出现了 "libc" 这个词。

**修复**：加入领域冲突惩罚 — 证据明显是堆/PE 时，ELF 栈题卡降权 80%；只有证据里出现该卡领域的锚词才放行。

### 发现 3：中文否定语境会误导

"图片能打开但 **zsteg 没结果**" → 修复前推荐"用 zsteg"。

**修复**：识别否定标记（没结果/没用/打不通），从查询中剔除被否定的工具；
但「主题词」（phar/ssrf/ssti）例外 —— "phar 打不通"是在问怎么打通，不是否定 phar。

### 发现 4：陷阱是真的有用，但只在方向对时

Pwn1 命中格式字符串卡后，卡片给出的坑：

> 64 位下地址含空字节会截断 strcpy，需把地址放在 payload 末尾

这条在本库 21 篇证据 WP 中反复出现，是真实踩过的坑。
基线思路（"用 %n 改 printf@got"）**没有提到这一点**，而这正是 64 位 fmt 最容易卡住的地方。

## 能力边界（诚实评估）

| 能力 | 状态 |
|---|---|
| 从证据定位技法方向 | ✅ 19/19 基准通过 |
| 给出该方向的真实陷阱 | ✅ 有效 |
| 在 macOS 上实跑 Linux ELF | ❌ 无 Docker/qemu user-mode |
| 完整利用链（盲打 BFS 需要 100+ 次交互） | ❌ 环境不支持 |
| Windows PE 逆向 | ⚠️ 无 Windows 环境 |

**本实验证明的是「知识库能把我引导到正确的方向」，不是「知识库能代替我做出题」。**
